# Куда — контракт API для бэкенда (MVP)

Клиент в `C:/kuda` использует JSON API с префиксом `/v1`. Этот контракт описывает **производственный сервер**; `mock/server.mjs` реализует его тестовую версию в памяти. Все комнаты, участники, набор кандидатов, голоса и итог должны храниться и вычисляться на сервере. Клиент не рассчитывает совпадения. Тестовые участники, которых мок добавляет при создании комнаты для одиночной проверки, не входят в производственный API.

## Общие правила

- HTTPS обязателен вне локальной разработки. JSON в UTF-8, даты в ISO 8601 UTC, суммы в рублях.
- Защищённые запросы: `Authorization: Bearer <session-token>`. `401 UNAUTHORIZED` означает, что клиенту нужен повторный вход.
- Ошибка: `{ "error": { "code": "ROOM_FULL", "message": "В комнате уже все участники." } }`. Код стабилен и пригоден для логики клиента; текст можно показать человеку.
- Клиент обновляет `GET /rooms/{id}` каждые 4 секунды, пока комната открыта. В ответе должен быть актуальный статус комнаты. В будущем можно добавить SSE/WebSocket, сохранив те же структуры данных.
- Не возвращайте голоса других участников до окончания раунда. `ownVotes` содержит только голоса текущего пользователя, `matches` — агрегаты.
- Для всех команд смены состояния сервер проверяет права и статус комнаты; `409` при конфликте. Для голосов клиент передаёт `Idempotency-Key`, повтор с тем же ключом и значением должен безопасно вернуть актуальную комнату.

## Авторизация и перенос гостевого профиля

| Метод | Путь | Тело | Ответ |
|---|---|---|---|
| `POST` | `/auth/guest` | `{ "name": "Аня" }` | `{ "token": "…", "user": { "id": "…", "name": "Аня", "method": "guest" } }` |
| `POST` | `/auth/email/register` | `{ "name": "Аня", "email": "a@example.org", "password": "…" }` | Такой же ответ; `method=email` |
| `POST` | `/auth/email/login` | `{ "email": "a@example.org", "password": "…" }` | Такой же ответ |
| `POST` | `/auth/telegram` | `{ "initData": "<сырая строка Telegram.WebApp.initData>" }` | Такой же ответ; `method=telegram` |
| `POST` | `/auth/max` | `{ "initData": "<сырая строка window.WebApp.initData>" }` | Такой же ответ; `method=max` |
| `GET` | `/me` | — | Объект пользователя |
| `DELETE` | `/auth/session` | — | `{ "ok": true }`; отозвать текущую сессию |

В браузере и мобильном приложении можно начать как гость. Если гость регистрирует почту или входит в уже существующий почтовый аккаунт, сервер привязывает/переносит его комнаты и голоса к постоянному `user.id`. Для переноса не нужно повторно голосовать. Конфликт двух голосов одного человека по одному заведению разрешается явно: сохранять ранее записанный голос постоянного аккаунта, а недостающие переносить; действие журналировать. На новом устройстве вход по той же почте возвращает этот `user.id`.

Для продакшена обязательны проверка почты, защита входа от перебора, хеширование пароля (Argon2id или эквивалент), отзываемые сессии и план ротации токенов. Нельзя передавать токены в URL. Вебу предпочтительна защищённая `HttpOnly` cookie с CSRF-защитой; текущий клиент хранит тестовый bearer-токен в `localStorage`, поэтому перед публичным запуском согласуйте смену транспорта с фронтендом. На iOS/Android токен хранится через `expo-secure-store`.

### Telegram и MAX `initData`

Клиент отправляет **сырую** строку `initData`; `initDataUnsafe` используется только как подсказка интерфейсу для параметра приглашения. Сервер:

1. Требует ровно один `hash`, без повторов параметров, ограничивает размер строки.
2. Проверяет HMAC-SHA256 по правилам соответствующей платформы и сравнивает подпись константным временем.
3. Проверяет `auth_date` (рекомендуемое окно — 1 час), наличие `user.id`, привязку к своему боту.
4. Ищет пользователя по паре `(provider, provider_user_id)`, создаёт или возвращает локальную запись и выдаёт собственную сессию.

Токены ботов остаются только на сервере (`TELEGRAM_BOT_TOKEN`, `MAX_BOT_TOKEN`). Тестовый сервер принимает настоящие подписанные строки, если эти переменные заданы. Режим `MOCK_ALLOW_DEV_AUTH=1` дополнительно принимает **только для локальной проверки** строки `mock:telegram:<id>` и `mock:max:<id>`; такой режим запрещён на публичном сервере.

Первоисточники алгоритмов: [Telegram Mini Apps](https://core.telegram.org/bots/webapps#validating-data-received-via-the-mini-app), [MAX: валидация данных](https://dev.max.ru/docs/webapps/validation), [MAX Bridge](https://dev.max.ru/docs/webapps/bridge).

## Условия встречи и каталог

`POST /catalog/estimate` принимает объект условий и возвращает `{ "count": 14, "minimum": 12 }`. Это число приблизительное и не резервирует заведения. `POST /rooms` повторно валидирует фильтры и запрещает комнату, если после них меньше 12 подходящих проверенных заведений (`409 NOT_ENOUGH_VENUES`).

```json
{
  "city": "Волгоград",
  "timeZone": "Europe/Volgograd",
  "date": "2026-10-06",
  "time": "19:00",
  "area": { "type": "district", "district": "Центральный" },
  "categories": ["cafe", "restaurant"],
  "budgetMax": 2000,
  "partySize": 4,
  "deadlineMinutes": 30,
  "exclusions": ["караоке"]
}
```

Для точки вместо района: `"area": { "type": "radius", "pointAddress": "площадь Павших Борцов", "radiusKm": 4 }`. Продакшен сервер геокодирует адрес либо возвращает `422 INVALID_AREA`, если точку нельзя найти. `date` и `time` означают местное время города в `timeZone`; сервер переводит его в UTC для хранения. `partySize` — 2–12, `deadlineMinutes` — 5–120. Проверяйте, что дата и время встречи в будущем и выбранные заведения подходят под бюджет, формат, область и размер группы.

Каталог первого пилота — Волгоград. Записи из парсера требуют ручной проверки названия, категории, адреса, координат, закрытия, часов и прав на фото/текст. Если цена или часы неизвестны, возвращайте `null` и текст вроде «Часы уточняются»; не утверждайте, что место открыто. Для производственной карточки возвращайте `photoUrl` (полный HTTPS URL проверенного изображения) либо `null`; клиент показывает заглушку при отсутствии фото. Поле `photoKey` есть только у нескольких демонстрационных карточек мока и сопоставляет локальные изображения, экспортированные из Penpot. Мок-сервер содержит вымышленные тестовые заведения, не готовый каталог.

## Комната, приглашение и состояния

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/rooms` | Создать комнату: `{ "constraints": { … } }`; ответ — `Room`, статус `waiting` |
| `GET` | `/rooms` | Комнаты текущего пользователя |
| `GET` | `/rooms/code/{code}` | Превью по временно действующему 4-значному коду |
| `GET` | `/invites/{opaqueToken}` | Превью по непрозрачной ссылке, доступно без входа |
| `POST` | `/invites/{opaqueToken}/join` | Войти в комнату; требуется сессия, повторный вход идемпотентен |
| `GET` | `/rooms/{id}` | Актуальная комната для участника |
| `POST` | `/rooms/{id}/start` | Организатор фиксирует общую колоду и запускает голосование; минимум 2 участника |
| `POST` | `/rooms/{id}/rotate-invite` | Организатор выпускает новую ссылку; старая сразу перестаёт работать |
| `POST` | `/rooms/{id}/cancel` | Организатор закрывает комнату до выбора места |
| `POST` | `/rooms/{id}/leave` | Участник выходит из комнаты; организатор использует `cancel` |
| `DELETE` | `/rooms/{id}/members/{memberId}` | Организатор исключает участника до определения результата. Исключённый не может вернуться по прежнему приглашению (`403 REMOVED`) |
| `POST` | `/rooms/{id}/finish` | Участник досрочно завершает после ≥10 оценок; сервер сохраняет голоса |
| `POST` | `/rooms/{id}/close-voting` | Организатор закрывает раунд после дедлайна либо завершения всех |
| `POST` | `/rooms/{id}/extend` | При пустом итоге добавить новые кандидаты всем, сохранив старые голоса |
| `PUT` | `/rooms/{id}/winner` | Организатор выбирает `{ "venueId": "…" }` из `matches` |
| `PUT` | `/rooms/{id}/booking-note` | Организатор ставит `{ "note": "booked_by_host" }` или `walk_in` |
| `POST` | `/rooms/{id}/reports` | Сообщить `{ "venueId": "…", "reason": "closed" }` или `incorrect_data` |

Превью: `{ "token": "…", "access": "active|selected|full|expired|cancelled|invalid|removed", "reason": null, "room": { … } }`. Оно показывает имя организатора, условия, число участников; при `selected` — победителя. Оно **не** отдаёт индивидуальные голоса и полную колоду. Участник, уже состоящий в полной комнате, может вернуться по ссылке.

Числовой код служит только удобным вводом. Для публичной комнаты нужен непредсказуемый токен приглашения минимум 128 бит. Ограничьте попытки кода по IP/устройству/аккаунту, срок действия и число присоединений; организатору нужен способ закрыть комнату и перевыпустить токен. Не записывайте полный токен приглашения в аналитику и общие логи. Ссылки для Web, iOS/Android Universal Links и Telegram/MAX `startapp` должны сохранять один и тот же токен комнаты.

Статусы MVP: `waiting → swiping → deciding → selected → completed`; отдельно `cancelled` и `expired`. Статус всегда меняет сервер транзакционно. Когда все закончили, комната остаётся в `swiping` до нажатия организатором «Посмотреть результат» (`close-voting`); после дедлайна сервер может сам перевести её в `deciding`. Повторное открытие ссылки на `selected/completed` показывает выбранное место. В `swiping` поздний участник получает тот же набор `candidate.id`, который был зафиксирован при старте.

Пример `GET /rooms/{id}` (поля опущены ради читаемости):

```json
{
  "id": "opaque-room-id",
  "code": "7120",
  "inviteToken": "available-to-room-members",
  "hostId": "user-1",
  "hostName": "Аня",
  "status": "swiping",
  "constraints": { "city": "Волгоград", "date": "2026-10-06", "time": "19:00" },
  "members": [{ "id": "user-1", "name": "Аня", "status": "swiping", "finished": false }],
  "candidates": [{ "id": "venue-1", "name": "…", "category": "cafe", "cuisine": "…", "district": "…", "address": "…", "priceHint": "…", "hoursLabel": "…", "tags": [], "photoUrl": null, "phone": null, "website": null, "mapUrl": "https://…" }],
```

## Голосование и совпадения

`PUT /rooms/{id}/votes` принимает `{ "venueId": "venue-1", "value": "like|dislike" }` и заголовок `Idempotency-Key`. Уникальное ограничение БД: `(room_id, user_id, venue_id)`. Повтор с тем же значением возвращает текущую комнату без второго голоса. Противоречивый повтор — `409 VOTE_EXISTS`. Нельзя оценивать место не из зафиксированного набора, после досрочного завершения участником или после окончания раунда.

Рекомендуемое правило, принятое для текущего клиента и мока:

1. `Q = max(2, ceil(0.75 × joined))`; в расчёте единогласия участвуют завершившие голосование, если их число достигло `Q`.
2. Сначала места, получившие `like` от **каждого** завершившего. Вернуть короткий список (`matchMode=unanimous`).
3. Если таких нет — места с `like` минимум от `ceil(0.6 × finished)` завершивших, `matchMode=majority`, показывая точную подпись «3 из 4».
4. Если кворума нет к дедлайну или большинства нет — топ до 5 по количеству `like` среди голосовавших, `matchMode=host_choice`, `incomplete=true` при незавершивших. Организатор выбирает явно.
5. Если голосов «подходит» нет — `matches=[]`, действие `extend`. Новая порция добавляется к общей колоде отдельной командой, старые голоса остаются.

Ответ `matches`: `[{ "venue": { … }, "likes": 3, "total": 4 }]`. Индивидуальные ответы других не возвращаются. Победителя подтверждает только организатор; сервер рассылает один `winner` всем. После перехода на большинство/выбор организатора клиент показывает причину, сервер должен сохранить `matchMode` для истории и аналитики.

## Итог, жалобы и аналитика

`winner` содержит адрес и как минимум маршрут; `phone` и `website` возвращаются только при наличии проверенных данных. `booking-note=booked_by_host` означает **ручную отметку организатора**, а не подтверждение рестораном. В MVP нет онлайн-слотов, оплаты или автоматического бронирования.

`POST /events` принимает `{ "name": "room_created", "properties": { "roomId": "…" } }`. События: `room_created`, `invite_opened`, `invite_shared`, `member_joined`, `voting_started`, `voting_finished`, `fallback_shown`, `winner_selected`, `booking_action`. Сервер должен также писать события изменения статуса самостоятельно, потому что клиент может закрыться до отправки аналитики. Не передавайте пароль, `initData`, токены, полные ссылки или персональные голоса в `properties`.

## Коды ошибок

`400 INVALID_JSON`, `401 UNAUTHORIZED|INVALID_CREDENTIALS|INVALID_INIT_DATA`, `403 NOT_MEMBER|HOST_ONLY`, `404 ROOM_NOT_FOUND|INVITE_NOT_FOUND`, `409 ROOM_FULL|ROOM_CLOSED|NOT_ENOUGH_VENUES|VOTING_CLOSED|VOTING_FINISHED|VOTE_EXISTS|TOO_EARLY|DEADLINE_NOT_REACHED|INVALID_WINNER|NO_MORE_VENUES`, `422 INVALID_CONSTRAINTS|INVALID_VOTE|INVALID_REPORT`, `429 RATE_LIMITED`. При сетевой ошибке клиент не продвигает карточку; повтор безопасен за счёт уникальности голоса и ключа идемпотентности.

## Локальная проверка

```powershell
cd C:\kuda
npm install
npm run mock
```

Во втором терминале: `npm run web`. Тестовый API слушает `127.0.0.1:8787` и хранит данные в памяти до остановки процесса. Для Android Emulator клиент по умолчанию обращается к `10.0.2.2:8787`; для физического телефона укажите доступный ему адрес через `EXPO_PUBLIC_API_URL` и запустите мок с `MOCK_HOST=0.0.0.0` только в доверенной локальной сети. Для опубликованного web-клиента задайте `EXPO_PUBLIC_WEB_URL` и HTTPS API. Мок содержит вымышленные карточки и не предназначен для публичного запуска.
